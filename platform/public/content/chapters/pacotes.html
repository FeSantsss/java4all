18

Pacotes & organização de projeto

Dificuldade: Iniciante-Intermediário
Pré-requisito: Interfaces

Até aqui, todo exemplo do curso viveu implicitamente em um único "pacote padrão". Em qualquer projeto real — e em todo projeto Spring Boot — o código é organizado em pacotes, que são pastas que refletem a estrutura de nomes totalmente qualificados das classes.

// arquivo: src/main/java/com/felipy/biblioteca/modelo/Livro.java
package com.felipy.biblioteca.modelo;

public class Livro { ... }

A declaração package precisa ser a primeira linha não-comentário do arquivo, e o caminho de pastas no disco precisa espelhar exatamente o nome do pacote. Para usar essa classe de outro pacote, você importa:

package com.felipy.biblioteca.servico;

import com.felipy.biblioteca.modelo.Livro; // import explícito
import com.felipy.biblioteca.modelo.*;      // import de tudo do pacote (evite em projetos grandes)

public class LivroServico {
    void processar(Livro livro) { ... }
}

A estrutura de pastas padrão do Maven (que o Spring Boot usa)

meu-projeto/
├── pom.xml                          // configuração do Maven (capítulo 19)
└── src/
    ├── main/
    │   ├── java/
    │   │   └── com/felipy/app/
    │   │       ├── Application.java
    │   │       ├── modelo/
    │   │       ├── servico/
    │   │       ├── repositorio/
    │   │       └── controlador/
    │   └── resources/
    │       └── application.properties
    └── test/
        └── java/
            └── com/felipy/app/     // mesma estrutura de pacotes, para os testes
Por que isso importa para o Spring: o Spring Boot organiza aplicações inteiras em pacotes por responsabilidade (modelo/domain, servico/service, repositorio/repository, controlador/controller) — uma aplicação prática do SRP (capítulo 16) em nível de projeto, não só de classe. Entender essa convenção agora evita estranhar a estrutura de qualquer projeto Spring Boot no primeiro contato.

Convenção de nomes de pacote

Por convenção (não exigência do compilador), pacotes usam domínio invertido em minúsculas: com.empresa.projeto.modulo. Isso evita colisão de nomes entre bibliotecas de fornecedores diferentes — é por isso que classes do JDK ficam em java.util, java.io etc.

O modificador de acesso "default" (sem palavra-chave, capítulo 04) — também chamado de package-private — só faz sentido quando você organiza código em pacotes de verdade. Ele é a ferramenta certa para esconder classes auxiliares de implementação que não devem vazar para fora do módulo (ex: uma classe ValidadorInterno usada só dentro do pacote servico), sem precisar deixá-las totalmente public.
